# AGENTS.md — правила работы агентов в этом репозитории

> Читай это ДО любого изменения кода. Суть: ты агент конвейера, твой тикет
> специфицирован в openspec, путь к сдаче — короткая ветка + тесты + дифф,
> который проверит человек и judge-модель.

## Словарь проекта

- **Спека** — `openspec/changes/<NNN-название>/`: `proposal.md` (зачем),
  `spec-delta.md` (какие требования добавляются), `tasks.md` (чеклист тикетов)
- **Тикет** — один пункт tasks.md с id вида `001-tc-01`: короткая задача,
  которую можно проверить запуск одного теста/сборки
- **Ядро** — `packages/core`: детекция скачков и матчинг, источников-агностик.
  Золотые фикстуры (golden fixtures) — эталон данных из Python-референса
  (`~/projects/lfstl/jump_news`); parity-тесты сверяют TS-ядро побитно

## Что тикет обязан соблюдать

1. Один логический шаг. Если дифф превышает ~300 строк — стоп, отчитайся
   и предложи декомпозицию, не продолжай.
2. Новая логика — только с тестом рядом (`*.test.ts`). Тест без логики и
   логика без теста не переходят в коммит.
3. TypeScript `strict`. Никаких `any` без комментария-обоснования.
4. Секреты не попадают в код: конфигурация через `.env`
   (шаблон — `.env.example`), ключи читаются в одном месте `packages/*/config.ts`.
5. Не трогай миграции схемы БД вне назначенного тебе тикета; миграция —
   SQL-файл в `packages/api/migrations/`, именуется `NNN_<slug>.sql`.
6. Не повышай версии зависимостей и не добавляй новых без указания в тикете.

## Цикл работы над тикетом (loop)

1. Прочитай спеку целиком и батч своего тикета; запиши план в начале
   сессии (план тикета).
2. Работай в отдельной ветке: `work/<NNN>/<slug>` от актуального `main`.
3. Ревью своего диффа перед сдачей: `git diff main` глазами — гонять ли
   лишние файлы?  Заглушенные тесты? Дебаг-выводы?
4. Сдача: коммит(ы) с сообщением в формате `(<NNN-tc-XX>) <что сделано>`,
   тесты зелёные локально `pnpm -r test`.
5. Если тесты упали — чини, не останавливайся на красном; после 3 неудачных
   попыток — стоп и отчёт (что блокирует, почему застрял, что пробовал).

## Judge-gate

Дифф каждого тикета перед мержем смотрит модель-судья другого вендора
с промптом из `judge/prompt.md`: соответствие спеке, отсутствие
галлюцинаций API, покрытие тестами. Verdict: approve / request-changes
— второе возвращает тикет в работу. Не пытайся «договориться» с судьёй:
исправляй суть замечаний.

## Операционное

- Параллельная работа агентов — через git worktrees (см. `orchestrator/README.md`);
  не работай в чужой ветке
- Логи прогонов агента сохраняй в `docs/runs/<дата>-<тикер>.md` — «прогон
  задачи» для демо строится из них
- Команды: `pnpm install`, `pnpm -r build`, `pnpm -r test`, `pnpm -r lint`
- Всё, что нужно человеку перед мержем, — шли в PR-описание кратко: что,
  почему, как проверил
