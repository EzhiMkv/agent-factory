# agent-factory

> Завод агентской разработки: тикеты из спеков → параллельные CLI-агенты →
> judge-проверка → мерж. Плюс продуктовая площадка, по которой этот конвейер
> гоняет задачи: коррелятор новостей и цен биржевых активов.

**Статус: скелет не собран. Отправная точка — [TZ.md](TZ.md) (продукт) и
раздел «Конвейер» ниже.**

## Зачем этот проект

Продукт здесь — не цель, а полигон. Цель — показать и отработать
**производственный сетап агентской разработки**: как инженер декомпозирует
спеку на короткие проверяемые тикеты, раздаёт их параллельным CLI-агентам
(Claude Code / Codex / opencode), и как результат проверяется тестами и
judge-моделью до мержа.

## Два слоя

### Слой 1 — продукт (полигон): коррелятор новостей и цен

MVP-описание и декомпозиция — [TZ.md](TZ.md). Стек:
TypeScript / Node, React, PostgreSQL / Supabase.

Данные — без рекламных кабинетов; основной ключ уже имеется (T-Invest,
только чтение):

- цены: T-Invest API — свечи по акциям TQBR вплоть до 1-минутных; новости
  API отдаёт с готовой привязкой к инструментам
- офлайн: MOEX ISS + RSS как безключевой запасной источник и генератор
  фикстур — демо и CI без сети
- тональность: LLM (ключ уже есть в doc2crm — OpenRouter)
- reference-ядро детекции скачков и матчинга — готовый Python-проект
  `~/projects/lfstl/jump_news`, переносится на TS с parity-тестами
  (детали в TZ.md)

### Слой 2 — конвейер

Планируемая структура репозитория:

```
├── AGENTS.md            # правила для агентов — единый вход для CI-агентов
├── openspec/            # спеки: proposal → spec-delta → tasks.md
│   └── changes/<фича>/  #   фича = набор мелких верифицируемых тикетов
├── orchestrator/        # очередь тикетов + диспетчер по параллельным агентам
├── worktrees/           # git worktree на агента (изоляция параллельных прогонов)
├── judge/               # gate перед мержем: judge-LLM ревьюит дифф против спеки
├── dashboard/           # метрики конвейера: тикетов/день, first-pass yield, $ на тикет
├── app/                 # слой 1: сам коррелятор (TS/Node/React)
└── docs/                # TZ, журнал прогонов, lessons learned
```

Как это читается на язык задач:

| Слово | Что у нас |
|---|---|
| specs | `openspec/changes/*/proposal.md` + `tasks.md`: тикет = короткая проверяемая задача |
| loops | прогон тикета агентом: план → код → тест → повтор по логам падения → сдача |
| оркестрация | `orchestrator/`: очередь тикетов, 3–5 агентов в worktrees, мерж по готовности |
| прогон задачи | лог одной задачи от спеки до мержа: что агент спросил, что judge отклонил, что правилось руками |
| judge перед мержем | `judge/`: модель-судья другого вендора ревьюит дифф против спеки; verdict — комментарий в PR |

Метрики конвейера ценны не менее, чем продукт: тикетов/день, доля
first-pass через judge, стоимость тикета, ночные прогоны в истории.

## Что делать следующей сессии

1. Прочитать [TZ.md](TZ.md) (продукт и MVP-декомпозиция).
2. Собрать скелет: `app/`, `openspec/`, `orchestrator/`, `judge/`,
   `dashboard/` (пусто-с-README, чтобы структура читалась).
3. Написать первую спеку `openspec/changes/001-ingest-prices/` и прогнать
   её через конвейер как пилотный прогон — это прообраз 30-минутного
   демо.
4. Judge-gate пока простой: дифф PR → judge-LLM → вердикт в комментарий.
   Вендор судьи ≠ вендор кодящего агента (их принцип).

## Принципы

- Конвейер важнее продукта. Фича продукта ценна в первую очередь тем,
  что даёт пачку тикетов для конвейера.
- Каждый тикет — короткий и проверяемый: код + тест + миграция/компонент,
  а не «сделай модуль».
- Никакого вайб-кода руками по их стеку: если задача правится руками во
  время демо — это отдельно показанный ручной фолбэк, а не тайный способ.
- Все секреты — в `.env` (`.env.example` обязателен), в репо не попадают.
